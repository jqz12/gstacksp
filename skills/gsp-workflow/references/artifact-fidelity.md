# SP 方法的产物检查与接口文档衔接

这是现有阶段的交接规则，不是 SP 正文的替代摘要。先读当前技能完整正文与所需附件，再检查它要求的真实产物。安装完整、技能表有名字、CLI ready 都不能单独证明方法已遵循。

## 在现有阶段落实

| 阶段 | 交接前核对的产物 | 现有记录落点 |
|---|---|---|
| brainstorming | 用户目标、约束、选定方案、可判定验收，保留原版讨论与 builder check；已有确认引用真实来源 | spec.md；选择及理由在 decisions.md |
| writing-plans | 执行原版文件责任设计、任务粒度、完整头部、Global Constraints、每任务 Files/Interfaces、具体步骤与验证 Expected，以及五项自查 | plan.md，包括简短 Self-Review/自查结果 |
| execute | 开始前读 spec/plan，逐对比较跨任务 Consumes/Produces 的签名、字段、失败与兼容约定；实施中核对实际测试及 Expected，偏离须裁决 | decisions.md 的 Pre-flight / Ruling；CLI 任务状态和 run 证据 |
| review | 既审实现质量，也比较原需求、计划、真实差异、验证和当前文档；指出计划本身的缺陷，不让测试通过掩盖需求遗漏 | review.md，发现、处理、未覆盖；必需项未处理不交付 |
| verify / ship | 逐项核实需求验收和适用方法的证据，披露未覆盖及裁决；技能顺序是执行归因，不当作流程合规证据 | 原 delivery.md，链接上述正本与收据 |

不为每项检查另建报告或让用户重复批准。小任务可以短，具体程度仍须足以让执行者判断下一步及成功条件。无程序接口写明确理由；无共享接口是核对后的结论，不能从缺失 Interfaces 推断。Review Focus 经检查无新增风险时写检查范围及理由，不凑五条假风险。

## 计划结构与内容两种检查

计划写完、按完整正文完成五项自查、登记完整任务后，运行：

```text
<gsp> plan-check <id>
<gsp> seal-plan <id> --check-structure
```

执行者遇到旧计划或不确定的交接时也先 plan-check，并阅读正文核实提示。工具检查显式标签/章节、登记任务、Files/Interfaces/Consumes/Produces、checkbox 和 Run/Expected。允许原版英文或支持的中文标签，代码块/注释不充当结构。Self-Review 是本项目把原版自查结果留在计划中的落点，不声称该标题来自原版。

失败时补充必要决策、按原封存规则重封存；排版不被识别时可调整本任务排版，不能把真实已有内容误报为语义缺失。工具不验证链接、签名一致性、需求覆盖或测试充分性；`semantic_review=NOT_CHECKED` 即使结构通过也不变。必须实际做原版自查、执行预检及审查。旧版不带开关的 seal-plan 为兼容保留，不能声称所有 CLI 调用已经受新结构门禁强制。

历史 ready 计划只能作为历史输入，不能因曾通过测试就直接作为合格模板，也不能为了新格式静默改写历史以声称当时遵循。若历史实现仍需返工，按实际任务恢复、重新封存和证据失效规则处理；无需为格式重做已正确实现。

## 接口变化的当前正本

涉及公开函数、CLI、HTTP、事件或跨模块数据契约时，在计划所属任务中明确：

- **接口边界**：消费者/生产者、精确名称与类型、关键错误行为、兼容/迁移要求；不把内部每个小函数都变成公共 API。
- **当前正本**：沿用仓库现有接口资料；没有时放 `docs/reference/` 相应主题。任务 spec/plan 记录当次决定，当前参考文档描述现在的行为，不长期双写。
- **维护来源**：人工文档则指定同任务更新；代码或 schema 生成则指定生成源、命令、产物位置，避免再建手写平行正本。
- **验证**：实际参数、示例、返回和失败行为与实现核对，接口改变时检查实际消费者和兼容性。HTTP 可使用已有 OpenAPI 工具；桌面 Rust 项目按类型、调用和事件边界说明；不强制引入新文档栈。

纯文案、无接口变化等不适用项写具体原因，不制造 API 文档或新审批。`gsp-document-generate` 按需辅助，所属实现任务仍负责同步，不能因未单独调用它而跳过当前文档维护。

## 工程职责的适用性与流转

这是同一主流程的职责参考，不增加一组必须逐个调用的技能。设计阶段沿本次真实变化判断下表；只展开会影响方案或验收的主题。可合并说明不适用原因，纯文案修正不必填写八行表、制造API或迁移文档。

| 本次可观察变化 | 需要落实的职责 | 原有落点与验证 |
|---|---|---|
| 新需求/行为/受影响消费者 | 正常与失败路径、非目标、约束、可判定验收 | spec；plan 将验收分配给任务与验证 |
| CLI/HTTP/IPC/事件/导出契约 | 输入输出、错误、分页、兼容与调用方；当前正本及生成方式 | 依本文件接口规则，同任务更新契约/说明并验证真实消费者 |
| 数据库/持久化/批量写入 | 老数据、约束/回填、幂等、失败重入、备份恢复；旧程序是否能读新状态 | spec/plan；代表性旧数据夹具、迁移中断与恢复验证；已有运行说明 |
| 参数/配置/依赖/运行环境 | 默认值、优先级、无效值、秘密来源、锁定版本、新环境启动/升级 | plan任务；安全配置示例与当前安装/使用说明；实际命令验证 |
| 跨模块/外部服务/质量目标 | 真实边界、超时后结果未知、重试副作用、并发、UI状态及适用安全/性能风险 | Review Focus与任务测试；mock不替代被其隔离的关键边界，按需专项技能 |
| 资料/生成器/测试或调试输出 | 当前文档正本、生成源、消费者、夹具/证据/临时产物位置与保留用途 | 同任务维护受影响资料；集中治理另按需调用，不每次全库搬迁 |
| 制品/安装/部署/自动更新 | 版本、目标环境、配置保留、升级失败、回滚与数据恢复、用户验收和授权 | plan/review/delivery及当前运行说明；核实实际制品与使用路径 |
| 引入持续运维责任 | 诊断、日志容量/脱敏/保留、依赖维护、恢复演练、经验纠错或停用 | 适用说明与任务；真实延期有来源待办及责任，必需工作不能延期换ready |

每个适用项形成同一条追踪链：**验收/风险 → plan任务 → 实际验证 → 当前文档**。已有文档和明确ID/链接足够，不为此再建账本或重复报告。仅准备发布时，记录待发布/待用户验收和执行者；发布、回滚与真实数据操作仍核对授权。

- brainstorming：将影响设计的职责写入spec；确认当前事实，不用未来设想覆盖当前说明。
- writing-plans：在已有Global Constraints、Review Focus、Interfaces、步骤和Self-Review内安排任务与证据。不增加plan-check必填章节；全局表不能替代实际任务步骤。
- execute：预检消费者/生产者和适用数据/配置假设；实际变化同步当前正本。新风险需裁决或更新计划，实质设计变更核对确认；普通已授权技术选择继续。
- review：比较原需求、适用主题和真实产物；验证文档/恢复等必要事项已完成，不能只检查测试绿或技能名称。
- verify/ship：在原review/delivery概述覆盖、实际证据、具体不适用原因、未覆盖项与下一责任人；沿用统一技能表。技术ready、已发布、业务验收分别陈述。

例如新增数据库非空列：先确认存量数据如何回填与旧版本兼容，再把迁移/恢复用例分配给实际任务，更新已有运行说明。只有口头“回滚程序”不构成数据恢复证据。无需为此另设一套固定审批或每个字段各建一份文档。

结构工具不能判断上述职责是否充分，原文保留或场景答题也不证明真实执行。使用项目证据说明结论；没有运行的恢复、真实第三方调用或安装环境明确写未验证。

## 后台worker与主控的分工

后台规划worker读取完整计划方法，完成正文自查并返回完整计划及一致的任务列表；收到job.plan_findings时修正候选。worker保持只读，不执行task-add、plan-check、seal-plan记账。主控在接纳前检查候选结构/大小，登记后再checked seal；预算、拒绝证据和恢复见[驱动器](driver.md)。会话内规划仍使用本文件前述CLI顺序。两者要求相同，执行命令的责任方不同。

## 交付披露

复用 review.md / delivery.md，简短说明“需求与方法覆盖”：已核对的规格验收、计划自查/接口预检、实际验证、当前文档及不适用理由。必要遗漏仍为未完成；公开所有裁决及接受延期的项，不能只列技能名。结构工具、原文保留、场景回答、真实项目执行四种证据分开说明。
