# 阶段交付与下一步

所有 GSP 技能共用本规则。它规定用户看到什么、任务如何接续，不替代 SP 的设计、测试、审查方法，不新增一套批准或独立状态文件。

## 阶段总结与任务回复

阶段边界、任务交付、阻塞或交接时，简洁说明：

1. **实际结果和状态**：完成了什么，仍有什么没完成；草稿、预览、检查通过、技术ready和真实业务交付分别表述。
2. **实际使用的技能**：名称、用途、对应产物或结论。区分“按技能执行”“仅参考”“未执行/未验证”；多代理注明实际来源。读取技能、宿主自动发现、工具调用和遵循技能不是同一件事，没有原生记录不冒称工具级调用证明。不要把审查的48个技能都列成实际执行，也不要为了清单齐全运行无关技能。
3. **证据与成果入口**：给用户可点击的真实文件/页面，说明本次实际验证及限制。已有文件复用，不每个技能另造报告；内部工具子步骤无需反复发送整套总结。
4. **下一步与责任**：指出具体动作、执行者和触发条件，明确“已继续”“将继续”“等待什么”或“当前目标已结束”。不能用空泛的“可以继续”“你想做什么”代替交接。

结果说明可以按任务规模精简，技能执行记录统一使用下方固定模板。解释必要内容，不机械填充空项，也不把主任务的阶段总结变成每次工具调用后的日志。

## 条件化接续

Git health 是工作流入口检查的一部分。AI 优先读取 health 输出的短 `route`/`handoff`，根据 `next_skill` 接续；不把完整报告塞入上下文。`clean` 且无用户决策时继续当前阶段，`needs-decision` 或 `blocked` 时只展示 route 指定的一项决策并记录一次；脏工作区、分支不匹配、detached HEAD、无仓库或未知状态使用 `gsp-git`。`gsp-git` 返回后回到 workflow，由 workflow 选择 brainstorming、execute、verify 或 ship，不重复询问同一 Git 问题。

- 当前目标内、已有授权、依赖满足：按现有模式继续下一阶段，不在可继续的阶段提前结束并等用户提醒。嵌套技能如freeze/TDD/browse/learn完成后返回调用者，失败按原任务进入调试/修复/阻塞。
- 仅报告或只读授权：交付发现和推荐整改范围，不自动执行修改。需要用户设计选择、新授权或手工操作时，准确说明所需动作、原因和来源，给命令/入口；已有选择不重问。
- 已明确授权连续执行或无人值守：同一已确认设计不重批，不因计划写完或固定收尾菜单机械等待；实质设计变更、超出授权或无法可靠推进仍按契约停下。普通会话不得擅自记录为无人值守。
- 当前需求完成：给一个有依据的推荐下一步及依赖；不能擅自启动另一个需求、付费实验、发布或清理。独立导出/查询任务可以结束，无需硬接其他技能。
- 尚未完成：不能只写建议后交还用户；能在授权内做的继续做。真正阻塞时保留证据、说明下一步由谁恢复，不能把未知标成功。

## 文档/目录治理专项展示

完整治理交付必须包括：**从实际文件系统核对的最终目录树、旧→新变化摘要、当前正本与历史/兼容入口、人与AI阅读顺序、例外及未完成项**。局部改动只展示受影响分支；数千任务用有限深度树加完整清单链接，不哈希/展开构建缓存。规划目录明确标“拟议”，不能冒充实际生成。

复用任务 governance.md 和 delivery.md，注明核对范围/时间，新增、移动、合并、原位保留分别说明；未执行迁移就写“未迁移”。代码交付也链接实际变更和使用入口，但不要求每次小修输出全仓目录树。

## 验证范围

生成测试只能验证规则是否进入最终技能，不能证明模型遵循。行为场景检查：赶工仍展示真实成果；仅检查不擅改；既有授权继续；必要人工操作有明确入口；技能清单不把参考当执行。hooks元数据不是技能合规证明。人工判断仍需真实项目后续验收。

## 最终任务总汇报（gsp-ship）

宣布独立开发/整改任务完成前，实际运行status或resume核对当前任务，再按workflow完成当前证据、review与ready；既有检查仍有效且状态已核实时不为形式重复运行。不能只阅读raw state/旧delivery或手工追加完成声明；health/索引不能替代任务收尾。嵌套技能返回父任务，只读咨询/独立文件导出等按自身范围结束，不强制为所有回答创建GSP任务。涉及过期验收且仍可推进时继续修复，不把补手续交还用户。

任务完成或交付准备时，gsp-ship负责在最终回复中汇总本次实际技能执行顺序，并在既有delivery.md保留可追溯的详细版本。它汇总已经发生的工作，不重新调用所有技能补齐名单。保留以下五项，技能表使用下方唯一模板，按规模减少行数。

1. **完成结果**：已完成目标、技术ready/实际交付状态及未完成事项。
2. **成果入口**：真实文件/使用入口；涉及完整文档治理时附实际目录树、差异和阅读顺序。
3. **验证与限制**：实际命令、结果、收据及尚未覆盖范围，不将旧版本验证冒充当前全部通过。
   结合[产物检查](artifact-fidelity.md)简述需求与方法覆盖，链接规格验收、计划自查/接口预检和当前文档；适用项未完成应如实披露。保留全部实际裁决及接受延期项，不能由技能名字推断方法遵循。
4. **技能执行顺序**：按实际发生顺序填表；连续重复可合并，审查→修复→重新验证的循环保留。嵌套方法可同一行说明调用关系；代理步骤注明来源。必要阶段未执行或沿用已确认设计时说明原因，仅参考的材料另列，绝不伪造调用时间/次数或原生发现记录。
5. **下一步**：具体推荐、执行者、是否当前授权内可继续，或等待的明确动作/条件。当前目标完成不擅自启动另一需求。

## 本轮技能执行顺序

阶段总结与最终交付使用同一标题和四列。标题固定为“本轮技能执行顺序”，表头与列序固定如下，不能改成箭头串、段落、另一种标题或另一组列名。小任务仍保留表格，只减少行数。日常进度消息和简单追问无需重复表格，形成阶段总结或最终交付时必须出现。delivery.md 使用同一格式保存本轮详细记录。

| 顺序 | 实际执行的技能 | 本次动作 | 结果/产物/证据 |
|---|---|---|---|
| 1 | `gsp-技能名` | 真实执行动作，代理注明来源 | 已核实结果或真实证据入口 |

填写时替换示例行。每行只列本轮确实按规则执行的技能，编号从 1 连续递增。按发生顺序记录，连续重复可合并；审查后修复及重新验证分别保留实际次序。嵌套方法注明所属步骤，代理注明来源，代理使用其他原版资源时如实标明，不能改名伪装为主会话执行。仅阅读但未执行的材料在表后用“仅参考”单列；没有实际执行的技能时表内写“无”，说明本轮属于何种直接回答。历史执行只作背景，不冒充本轮执行。

最终回复必须包含顺序摘要，不能只让用户点文件寻找；任务很小时表可只有一两行。清单是按会话与证据如实归因的过程说明，不单独证明流程合规。不要为满足格式新增一份竞争正本或每个工具调用一行日志。
