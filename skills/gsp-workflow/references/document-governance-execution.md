# 文档治理执行规则

与 [共同治理契约](document-governance.md) 共用分类、路径和 CLI；本文件规定 AI 如何执行，不新增机器状态正本，也不宣称 CLI 已强制语义验收。

## 选择本次范围

- 新项目：建立实际需要的 README、宿主协作入口及文档阅读路径；按阶段生成任务材料，不批量创建空目录或空报告。
- 老项目完整接入/集中治理：覆盖已约定文档范围，逐份阅读并分类、明确正本、执行迁移及验收。若工作量大可分批，但未完成批次仍属未完成，不能用预览代替整体交付。
- 日常开发：只检查改动影响的当前说明、接口、模块关联和任务材料；没有影响则记录理由。不默认全库扫描、迁移或另建一轮设计审批。

health 只报告问题。只有检查授权时，提供整改范围和建议后等待整改授权；已有整改授权则在范围内直接衔接本技能，不重复问。沿用已有设计和计划；旧 freeze 记录只作历史读取。所有实际整改必须关联有效执行任务，不能只把“复杂迁移”纳入GSP。开始前核对实际 Git 差异、其他会话、活跃任务和真实资源归属，不能清锁或覆盖他人工作。

## 修改前：确认本次属于哪条执行路径

| 使用方式 | 必须做的动作 | 结束位置 |
|---|---|---|
| 独立治理需求 | 读取workflow/共享契约；先核对active，再resume实际任务；无项目时init。确认spec/plan覆盖本次真实目标。没有适用任务则new；原任务已ready/关闭或原目标只是预览，不能仅复用它的文件夹，须明确新任务或正式返工 | 本次任务有效run、review、ready，随后ship |
| 开发中的嵌套维护 | resume父任务，确认当前实施任务和授权范围；必要时更新计划并封存。复用父任务，不另建重复审批/账本 | 返回父任务执行点，由父任务完成最终验证/审查/交付 |
| 仅检查/咨询 | 使用health或只读分析，输出发现与建议；不改目标资料，不为报告强建开发任务 | 报告检查范围和限制；不能称整改已完成 |

`resume`可能撤销过期ready，这是正确核验，不是丢失已完成工作。新任务用正常设计/计划记录已确认目标，不重复询问同一授权；范围实质改变才按真实对话确认。返工用task-reopen → task-start；规格变化使旧批准失效，按实际授权approve，再seal-plan。不得编造quote或绕过活跃任务/资源租约/驱动保护。原任务在另一会话执行时先协调，不能切换或重开他人任务。

每次独立整改都要能回答“本次run ID、实际spec/plan路径、当前实施任务是什么”。仅阅读active.json、技能文档或旧delivery，不算恢复核验。读取规则以后必须实际执行适用命令，不能用总结文字代替。

## 执行闭环

1. 从实际用户指示提取目标和完成条件，并与 spec 对照。目标缺失时修正规格；目标有实质变更按正常设计确认。不能把“完整改造”私自收窄为“完成盘点”。
2. 完整治理读取 health 报告及原始文档；日常直接核对受影响资料，已有相关报告则复用。目录名、年龄、字节重复和链接数量不足以判断语义。确认资料是当前有效说明、任务历史、研究、运行验证、混合内容或待核实。
3. 在本任务已有档案内维护 `governance.md`，同一份文件承载清单、执行记录和验收，避免再建多个并行清单。已有等价清单则复用。逐项字段见下表；目录聚合项只用于索引，不能代替逐文件归属。
   完整治理先记录约定目录、文件类型和有理由的排除项，覆盖根目录资料、非Markdown证据和本地工作产物；读取asset_scan范围与未递归目录，按实际项目补足约定资料根目录；保留原始清单与可用的 Git 版本、文件摘要或迁移收据。收尾重新盘点，核对新增、遗漏、删除及内容漂移，不能仅凭表内全部打勾推断覆盖完整。存在其他会话改动时重新核实，不覆盖或复用失效的内容判断。
4. 当前有效内容按需归入 product/reference/howto，任务历史归入 archive 或保持有效任务绑定，研究归 research，运行验证归 ops。README、宿主指令、工具要求的 DESIGN 可保留入口。混合规格须逐章节核实、提炼当前说明并保留来源，不能整包归档假装已完成。
5. 使用 docs-search/module-set/work-link 维护有用的身份和关联；模块职责与历史关系须内容核实，不自动从改名推断。无需给每个普通文件制造模块。
6. 普通文档用 docs-move 预览后按既有授权 --apply，保留旧入口及备份，复查支持范围以外的引用。执行绑定材料被拒绝时不得绕过；需重新绑定则用 documents-adopt，披露批准/证据失效并按真实授权恢复。未知资料不能自动删除；迁移失败按 docs-move-recover 调查恢复。
   documents-adopt 不是移动文件或覆盖活跃会话的许可；先解决在场执行与文档保护约束，不能用重新关联绕过迁移拒绝。
7. 资料整改同时核对生成脚本的输出目录、引用与保留规则，避免后续运行继续把产物写到根目录。原始采集、精选证据和研究结论分别记录，失败日志按排障用途处理。普通工程配置按工具要求保留。更新当前阅读入口和必要说明，重建 docs-index；完整治理运行 health 复查；日常核对受影响内容、正本、关联及外部消费路径，必要时才做全量 health。health 无错误仅证明对应结构检查，不等于语义正确。受影响的测试/发布文档另作明确检查，不能用默认排除档案的源码指纹宣称覆盖。
8. 最终审查将用户目标、spec、清单实际结果逐项对齐。必需工作未完成仍阻塞；延期必须有真实范围决定及待办来源、影响和下一步，不能只登记待办就消除阻塞。

## 修改后：闭环不能停在health

独立治理按实际任务执行task-start → 修改/迁移及明确文档检查 → run登记检查收据 → task-done；全任务结束后运行最终`run --task all`，先写当前review.md再登记`review`，使用`ready`核验当前批准、计划、证据、审查与待办，最后由ship补充交付。非测试文档检查用`--kind check`，任务登记时写具体`--no-tests-reason`，不为了文档迁移盲跑全部业务测试。

health报告、docs-index成功和git diff --check各自只是检查证据，不等于上述任务登记或最终验收。将真实检查通过GSP run保存；如直接运行了检查，应明确是否尚缺任务证据，不能手改旧receipt。

嵌套维护完成后返回父任务，不在中间独立宣布整项需求完成。任何会影响验证输入的资料修改都要在最后验证之前完成；验证后又改产品说明，必须重新核验受影响证据。

禁止只向旧delivery.md追加“补验完成”后沿用旧READY标题。独立任务未完成当前review/ready，或状态核验已过期时，只能报告实际“已迁移/结构检查通过，收尾未完成”，并在授权内继续。原始state.json的ready字样不是即时有效性证明，文件编辑不会自动触发后台失效刷新。

| 来源文件 | 内容用途/当前效力 | 唯一正本或目标 | 模块/任务/引用关系 | 处理动作与实际阶段 | 验证证据或例外理由 |
|---|---|---|---|---|---|

例外可以是正确结果：有工具路径约束的现行规范可原位保留；必须有原因、阅读入口和正本标识。保留旧链接跳转入口不算两份正本。无法确定内容效力的资料写待核实，不伪造完整。

## 阶段与交付措辞

- 已盘点：找到并阅读约定资料，尚未保证归位。
- 已预览：已给出处理方案，尚未执行。
- 已迁移：实际操作完成，仍须检查引用与内容。
- 已验收：约定范围内正本明确、必要操作和复查完成；保留例外有依据，必需未完成项为零。

阶段是人读治理记录，不冒充 CLI 状态或用户业务验收。交付链接 governance.md、health 报告、实际迁移结果和相关证据，并分列范围、当前阶段、例外、未完成与下一步。任务 ready 本身不能证明完整治理。

按 [交付与衔接](output-handoff.md) 展示从文件系统核实的最终目录树、旧→新差异、正本/历史/兼容入口、人与AI阅读顺序，以及实际技能清单和下一步执行者。局部仅相关分支，大规模用有限深度树加完整清单，不能将规划树当实测成果；未迁移明确说明。
